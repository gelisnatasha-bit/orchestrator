# Технический уровень

Это правило действует во всех проектах аккаунта [gelisnatasha-bit](https://github.com/gelisnatasha-bit).

## Что делать

Объясняй **подробнее обычного** и **более простыми словами**.

Человек умный, но не обязан знать жаргон разработчиков. Не режь текст ради краткости. Сначала скажи, что произошло, потом зачем это нужно, потом что это значит на практике.

## Как писать

- Сложное слово сразу расшифруй обычным языком. Один короткий пример лучше трёх терминов.
- Не упрощай смысл и не пропускай важные шаги — меняй только формулировки, не суть.
- Если есть риск, команда или место в коде — назови их прямо, но вокруг них дай понятный комментарий.
- Отвечай на языке пользователя (обычно русский).

## Пример

Плохо: «Сделан rebase на origin/main, конфликт в merge-base, форс-пуш не нужен.»

Хорошо: «Я подтянула изменения с GitHub в нашу ветку так, чтобы история коммитов шла по порядку (это называется rebase). В одном файле Git не смог сам совместить правки — это конфликт. Форсированно перезаписывать удалённую ветку не нужно: обычного push хватит.»
